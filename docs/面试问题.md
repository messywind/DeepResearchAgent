## 1. 请介绍一下这个项目

### 面试回答主线

这个项目实现的是一个 **Deep Research Agent**，整体采用 **多智能体架构**。

由一个 **Supervisor Agent** 统管全局：先生成研究报告的提纲和初始草稿，再把不同的研究任务委派给多个 **Research Agent** 并行执行。Research Agent 负责搜索和补充信息，随后系统不断根据新证据对报告进行完善、精修和“去噪”。

报告迭代的核心思想参考了 Google 的 **TTD-DR（Test-Time Diffusion Deep Research）**：把报告从粗糙初稿逐步修正到高质量终稿的过程，类比为扩散模型从噪声状态逐步去噪的过程。

为了让这个去噪过程更稳定，项目中又加入了两类反馈：

- **红队 / 对抗 Agent**：专门攻击当前报告，发现显性和隐性的逻辑问题、证据不足等缺陷；
- **Evaluator Agent**：从多个维度给报告打分，同时给出打分原因。

红队反馈和 Evaluator 的评分结果都会回传给 Supervisor，由 Supervisor 决定下一轮如何修改，于是形成：

`生成/优化 → 反馈 → 再优化 → 再反馈` 的闭环，最终输出完整的调研报告。

### 回答时一定要提到的关键词

1. **多智能体架构**；
2. **Supervisor + Research Agent 的分工**；
3. **TTD-DR 的迭代去噪思想**；
4. **红蓝对抗 / 红队批评机制**；
5. **Evaluator 量化评分与反馈闭环**。

### 老师强调的回答思路

这道题不需要一上来陷入代码细节，而要先把整个项目的“主干”讲清楚：**它解决什么问题、整体架构是什么、最有辨识度的设计是什么、最终如何形成闭环。**

## 2. 这个项目的难点或挑战是什么

### 面试回答主线

这个项目最主要的挑战可以概括为两个：

1. **如何提升最终报告的质量**；
2. **如何减少大模型生成的幻觉。**

这两个问题并不只属于这个具体项目，而是 Deep Research 类系统普遍存在的核心问题。

### 挑战一：报告质量

“生成一个长得像报告的东西”并不难，真正困难的是让它达到人类、尤其是专业人员愿意采纳的质量。

几类重点质量问题：

- 某些论述缺少可靠引用支撑，导致结论偏颇；
- 模型为了产出“专业内容”，可能生成看似合理但其实没有依据的判断；
- 模型可能主动规避自己没拿到的信息，甚至本来能继续搜索，它却懒得找；
- 为了把报告写长，大量堆砌资料摘要，却缺少批判性分析；
- 内容很多，但缺少真正的 insight、深度整合和逻辑连贯性，最后只是“很长的水文”。

### 挑战二：幻觉

Deep Research 最危险的一类问题是：报告表面看起来非常专业，但事实本身可能是错的。

幻觉包括：

- 编造不存在的文献；
- 错误归因，把某个结果归到错误原因上；
- 篡改或误写标题；
- 杜撰实验；
- 杜撰数据。

很多问题只看最终文字表面并不容易发现，因此必须通过检索、验证和反馈机制约束。

### 最后一定要回到项目方案

讲完挑战后不能停在问题层面，要把它“绕回项目亮点”：

> 因此项目里引入了 TTD-DR 的迭代去噪思路，再结合红队对抗分析以及可量化的报告质量评分，让每一轮都能根据具体反馈去补证据、修逻辑、减少幻觉，最终生成逻辑更合理、证据更充分的报告。

### 老师强调的回答思路

面试官问“你这个项目最难的是什么”，很多时候真正想考的并不是某一段代码，而是：**你是否理解这一类系统真正难在哪里。**

## 3. 为什么要先生成提纲？有没有对比过有提纲和没提纲的效果？

这道题要分两部分答：

1. 为什么需要提纲；
2. 有提纲和没提纲的差异是什么。

### 一、为什么先生成提纲

#### 1）任务分解

生成研究提纲，本质上是在把一个模糊、开放、复杂的问题做结构化分解，变成一组可执行的研究子任务。

例子：

> “分析新能源行业未来五年的趋势。”

这种问题不适合一次搜索直接解决，可以拆成：

- 政策环境；
- 技术路线；
- 市场规模；
- 竞争格局；
- 其他相互独立的研究维度。

拆完以后，每个研究单元可以独立执行，甚至并行执行，从而缩短整体研究周期。

#### 2）规划与执行分离

提纲还相当于研究计划。

先规划，再执行，可以在消耗大量搜索、模型调用和计算资源之前先检查研究方向是否正确。

进一步还可以把提纲展示给用户，让用户先确认、编辑研究计划，确认后再执行。

老师举了 Gemini Deep Research 一类产品作为例子：先展示研究计划，让用户调整、确认，再正式执行。

这种流程的价值是：

`规划 → 用户确认 → 执行`

如果一开始方向就错了，可以在执行前修正，而不是等报告全部生成完才发现不符合要求，造成资源浪费。

#### 3）全局上下文管理

这是录音里特别强调的一点。

在多 Agent 系统中，不同 Research Agent 往往彼此看不到对方的完整上下文，每个子 Agent 只知道：

- 全局提纲；
- Supervisor 分给自己的当前子任务。

因此，**统一提纲就是所有 Agent 共享的全局参照物。**

它能让每个 Agent 知道：

- 整个研究准备覆盖哪些内容；
- 哪些内容已经覆盖；
- 哪些还没覆盖；
- 自己当前负责的部分处在整体结构里的什么位置。

即使子 Agent 之间不直接通信，只要都能看到同一个全局提纲，也能维持研究方向的一致性。

### 二、有提纲和没提纲的效果差异

录音中的回答是：项目里做过对比，没有提纲时效果明显更差，主要表现在：

- **报告结构难以控制**，多运行几次，整体结构变化会很大；
- **报告长度明显更短**。

### 三、这道题最后可以再升一层

老师特别强调：

> “有没有把提纲展示给用户”并不是本质问题。

真正关键的是：

- 系统内部有没有做 **结构化任务规划**；
- 有没有做 **全局上下文管理**。

有些产品可能不会显式展示提纲，但内部仍然会进行规划和迭代。显式展示提纲最大的额外价值是提高 **透明度和可控性**。

## 4. Supervisor 主要承担哪些功能？

### 面试回答主线

项目是多智能体架构，**Supervisor 是统管全局的主 Agent，也是系统的决策和协调中心。**

它能够看到相对完整的系统状态，例如：

- 当前研究提纲；
- 当前报告草稿；
- 各个 Research Agent 返回的研究发现；
- 红队对当前报告的批评；
- Evaluator 的质量评分；
- 各项评分对应的原因。

因此 Supervisor 相比子 Agent 拥有接近“上帝视角”的全局信息，然后基于这些信息决定下一步做什么。

### 核心职责

可以归纳为：**规划 + 协调。**

具体包括：

- 任务规划；
- 子任务分发；
- Agent 调度；
- 全局上下文维护；
- 报告迭代；
- 根据反馈决定下一步研究或修订动作。

### 一句话总结

> Supervisor 本质上不是“亲自干活”的 Agent，而是整个研究流程的规划、调度和决策层。

## 5. 如何让 Supervisor 和子 Agent 高效协作？多 Agent 怎么分工？

### 整体分工

- **Supervisor**：决策、调度、任务分发、维护全局上下文；
- **Research Agent**：负责实际搜索和深度研究；
- **红队 Agent**：对报告做对抗式批评；
- **Evaluator Agent**：做质量评估与打分；
- **写作 Agent**：在最终阶段负责整理和生成报告。

### 多 Agent 协作的三个基本原则

#### 1）主 Agent 不做具体执行

Supervisor 只负责决定：

- 做什么；
- 什么时候做；
- 交给谁做。

它不亲自去搜索、分析所有网页等具体执行动作。

#### 2）子 Agent 不拥有全局决策权

每个子 Agent 只关注自己的子任务，不跨任务做决策。

例如 Agent A 不应该介入 Agent B 的思考和决策。

#### 3）全局上下文由 Supervisor 统一维护

所有子 Agent 的结果最终都汇总到 Supervisor，再由 Supervisor 决定下一步。

也就是说：**系统只有一个全局协调中心。**

### 对子 Agent 的工程要求

#### 1）职责单一

一个 Agent 尽量只做一件事情。

如果一个 Agent 能完成，就不需要为了“多 Agent”而硬拆；只有比较、调研等天然需要分工的任务才值得拆多个 Agent。

#### 2）接口清晰

主 Agent 和子 Agent 之间最好通过 **结构化状态 / 结构化数据** 通信，而不是完全依赖自然语言随意传递。

录音里提到，项目中的状态流转是结构化的，所以能够清楚看到 Agent 输入、输出和状态变化。

#### 3）支持失败降级

某一个子 Agent 搜索失败、挂掉或没找到结果，不能让整个研究任务直接失败。

单点故障要能够被系统吸收，继续完成全局任务。

#### 4）可观测性

多 Agent 协作过程必须：

- 可记录；
- 可回放；
- 可调试。

需要能看到：

- 每个节点如何跳转；
- 调用了哪些工具；
- 工具输入是什么；
- 工具返回是什么；
- 哪一步发生异常。

录音中提到可以结合日志和 **LangSmith** 一类工具做定位。

### 一句话总结

> 多 Agent 高效协作的本质是 **规划与执行分离**：Supervisor 负责“做什么、什么时候做、谁来做”，子 Agent 负责“具体怎么做”。

## 6. Research Agent 主要调用哪些工具？有没有考虑更多工具？

### 当前项目里的主要工具：Tavily

项目主要使用 **Tavily** 作为搜索工具。

老师给出的理由主要有：

- 普通搜索 API 往往只返回链接和零散摘要；
- 如果把大量原始网页直接塞给模型，会消耗很多 Token，效果也未必稳定；
- Tavily 返回的信息已经做过一定程度的结构化、提炼和去噪，更容易直接注入 LLM 上下文；
- 除了普通网页，还可以用于检索论文等高质量内容。

项目里希望尽量使用：

- 官网；
- 论文；
- 其他高质量来源。

原因是这些来源比普通杂乱网页更适合给报告里的关键论点做证据支撑。

### 如果继续扩展，可以增加哪些工具

#### 1）代码解释器 + 文件系统

这两类工具通常可以配套使用。

代码解释器让 Agent 可以执行复杂计算和程序；文件系统让 Agent 可以：

- 读写文件；
- 查找文件；
- 保存中间结果；
- 做缓存和持久化。

为了避免生成代码直接影响本机，最好在 **Sandbox / 沙箱环境** 中运行，例如虚拟机或远程隔离环境。

#### 2）多模态工具

如果未来不仅生成纯文本报告，而是希望生成包含图片、音视频等富媒体内容的报告，可以加入：

- OCR；
- 图片搜索；
- 多模态大模型（MLLM）；
- 图片 / 音视频理解工具。

这样 Deep Research 就不再只研究纯文本信息。

### 这道题真正考什么

老师认为它主要考察：**你对 Agent 外部工具生态有没有足够了解，以及能不能说出项目未来的扩展方向。**

## 7. 项目里的“稳定去噪”具体是怎么做的？

这是项目最核心的一道题。

### 传统 Deep Research 的问题

传统系统常见的是比较线性的流程：

`搜索 → 汇总 → 回答`

问题在于缺少：

- 反复查证；
- 反复修订；
- 针对当前报告缺陷继续搜索的机制。

### 项目的核心：TTD-DR 式迭代去噪

项目把报告生成类比为图像扩散模型中的去噪过程。

先得到一个粗糙、不完整、不完全准确的初始报告，然后逐轮补充证据、修复问题。

完整循环可以概括为：

`V0 草稿`

→ 分析知识缺口  
→ 生成新的搜索问题  
→ 检索新信息  
→ 综合答案  
→ 修订报告  
→ 得到 V1  
→ 再分析 V1 的缺口  
→ 继续循环……  
→ 最终终稿

每一轮修订，本质上就是一次“去噪”。

### 为什么说是“稳定”去噪

关键在于加入了 **红蓝对抗 / 红队反馈机制**。

- **蓝方**：负责生成和优化报告；
- **红方**：负责攻击报告，主动挑毛病。

红方会重点检查：

- 逻辑是否严密；
- 引用是否正确；
- 是否缺少事实性信息；
- 语言是否流畅；
- 专业性是否足够；
- 是否还有隐藏缺陷。

然后这些批评全部回传给 Supervisor，Supervisor 下一轮优化时就会有明确目标。

因此它不是“模型自己凭感觉重写”，而是：

`报告 → 找缺陷 → 反馈缺陷 → 定向优化 → 再检查`

形成稳定闭环。

## 8. 报告质量打分考虑哪些维度？每个维度的标准是什么？

### 为什么不用一个总分

项目没有只给报告一个笼统总分，而是从多个维度分别打分。

老师强调：多维度评分比“整体打一个分”能给 Supervisor 更细粒度的优化信号。

### 三个评分维度

#### 1）全面性（Comprehensiveness）

关注：

- 是否完整覆盖研究简报 / 提纲要求；
- 是否存在明显遗漏；
- 关键部分的信息是否缺失。

#### 2）准确性 / 对齐度

这里录音中的“准确性”更偏向 **报告是否和研究提纲、研究目标保持一致**：

- 内容是否符合当前提纲；
- 是否出现明显跑题；
- 最终报告是否偏离研究任务。

#### 3）一致性（Consistency）

关注：

- 组织结构是否清晰；
- 语言是否清楚、专业；
- 逻辑是否存在漏洞；
- 前后是否自相矛盾。

### 打分方式

- 每个维度：**0–10 分**；
- **8 分以上**为优秀；
- 除了分数，还必须给出 **具体打分原因**。

最后把：

- 各项分数；
- 各项评分理由；
- 历史分数变化；

全部反馈给 Supervisor。

### 阈值告警

当平均分低于某个阈值时，可以触发质量修复提醒。

录音举例用了“低于 6 分”，其核心不是 6 这个固定数字，而是：

> 低于质量阈值时，要让 Supervisor 在下一轮优先修复报告，而不是继续无目的扩展。

### 为什么这也形成闭环

上一轮的评分和原因，会成为下一轮优化的输入，所以：

`评分 → 找到具体短板 → 下一轮针对性修复 → 再评分`

同样是自迭代过程。

## 9. 网页内容很长，怎么做上下文工程，避免上下文爆炸和干扰？

录音把方案概括成两个核心词：

1. **隔离**；
2. **压缩**。

### 一、隔离

不同 Research Agent 之间不直接共享完整上下文。

每个 Agent 只看到自己需要的信息，因此不会把其他 Agent 的：

- 搜索结果；
- 思考过程；
- 工具调用历史；

全部堆进自己的上下文。

这能显著降低上下文长度和信息污染。

### 二、压缩

Research Agent 也不会把全部原始搜索内容原封不动返回给 Supervisor。

录音中的流程包括：

#### 1）URL 去重

先清理重复 URL，避免同一来源反复占用上下文。

#### 2）提取和主题相关的信息

只保留网页中与当前研究 Topic 相关的部分。

#### 3）增加 Compress 节点

每个 Research Agent 的 ReAct 历史里会混有很多不同内容：

- 内部 Thought / 思考；
- Tool Call；
- 搜索摘要；
- AI Response；
- 其他中间记录。

并不是所有内容都值得传给 Supervisor。

因此项目加入专门的 **Compress 节点**，负责：

- 读取整个 Research Agent 的杂乱执行记录；
- 过滤掉不需要的角色和思考过程；
- 压缩剩余信息；
- 输出清晰、完整、引用规范的研究摘要。

最终 Supervisor 收到的不是一坨执行日志，而是一份干净、简洁的研究结果。

### 三、进一步扩展：写入 + 检索

如果上下文再长，单纯压缩还不够，可以把长期信息写到：

- 数据库；
- 文件系统；
- 长期记忆。

需要的时候再检索相关部分，而不是一次把全部历史重新塞给模型。

检索时可以结合：

- 字面检索；
- 语义检索；
- Embedding 相似度。

核心思想是：**用多少，取多少；只取当前 Query 相关的内容。**

## 10. URL 去重后每次最多取多少条？要不要对 URL 排序？怎么排？

### 当前项目的设置

录音明确提到：**每次最多返回 3 条结果。**

当前项目没有再单独做复杂的 URL 排序，原因包括：

- Max Result 只有 3，本身不大；
- 读取这些内容的耗时还能接受；
- 上下文不会因此明显过长；
- Tavily 返回内容本身已经做过一定整理和压缩。

### 什么场景需要 URL 排序

如果做更深层的网页搜索，例如：

- 搜到一个网页；
- 网页里又有大量超链接；
- 再继续向下展开；

此时可能出现几十、上百个 URL。

如果把所有页面全部加载，成本和上下文都会迅速失控，所以需要先排序、筛选，只留下高价值 URL。

### URL 可以按哪些维度排序

录音列举了这些维度：

#### 1）时间 / 更新时间

对于新闻、金融、股票等强时效主题，新内容通常权重更高。

#### 2）域名权威性 / 热度

例如：

- 官方网站；
- 高权威机构网站；
- 知名公司的官方域名。

通常比不知名网页更值得优先读取。

#### 3）网页是否可访问

有些站点存在：

- 反爬；
- 权限控制；
- 无法正常打开。

即使搜索结果相关，如果实际取不到内容，也应该降低优先级。

#### 4）相关度

搜索引擎本身通常已经做过相关度排序，但系统还可以按自己的 Topic / Query 再做一层相关度打分，例如通过专门模型或 Embedding。

### 最终排序方式

可以给不同维度设置权重，算综合分：

`综合分 = 时间分 × 权重 + 域名分 × 权重 + 可访问性 × 权重 + 相关度 × 权重 + ...`

然后只取 **Top-K URL**。

### 排完 URL 后，网页内容怎么处理

录音重点比较了两种方法：

#### 方案 A：分块（Chunking）

把长网页切成多个 Chunk，再类似 RAG 一样检索与当前 Query 最相关的片段。

优点：

- 细节保真；
- 精确检索能力强。

缺点：

- 上下文和检索压力较大；
- 信息容易碎片化；
- 可能缺失全局连贯性。

#### 方案 B：摘要（Summary）

让模型把网页整体压缩成与 Topic 相关的摘要。

优点：

- 压缩率高；
- 全局脉络更连贯。

缺点：

- 可能丢失关键细节；
- 摘要模型如果判断错误，会把真正重要的信息压没。

#### 组合使用

老师认为现在很多系统会把两者结合：

- **Chunk**：用于精确查细节；
- **Summary**：用于全局压缩和长期上下文管理。

这样兼顾局部精度和整体上下文长度。

### 术语说明

录音提到这类“URL 排序 + 分块”的思路与 **Jina AI** 的 Deep Search 工作相关。

## 11. 项目有没有用 Agent Skills？如果要加，怎么扩展？

### 当前项目为什么没用 Skills

当前项目做的是一个 **通用 Deep Research Agent**，所以没有额外加入面向某个垂直领域的 Agent Skills。

### 什么场景适合加 Skills

如果未来要做垂直领域研究，就非常适合加入 Skills。

录音里的例子包括：

- 金融研究；
- 某些金融因子的固定计算流程；
- 必须通过特定渠道获取数据；
- 需要和某个 App 做深度交互。

这类场景存在明确、可复用的专业流程，适合封装成 Skill。

### 在当前架构里怎么扩展

老师给出的思路参考 Deep Agent 类框架：

1. 在工具 / Skills 目录里增加 Skill 对应的 Markdown 文件和资源文件；
2. 每个 Skill 先提供元数据，例如：
   - Skill 名称；
   - Description；
3. 构造 Research Agent 的 System Prompt 时，先动态注入这些 Skills 的元数据；
4. 只有模型真正需要某个 Skill 时，再加载它的完整内容；
5. 用 **LangGraph Middleware** 一类机制实现这种懒加载。

### 为什么要懒加载

不是一开始把所有 Skill 的完整说明全部塞进上下文，而是：

`先告诉模型“我有哪些 Skill” → 需要时再加载具体 Skill`

这样可以减少上下文浪费。

## 12. 除了 LLM-as-a-Judge，还知道哪些 Deep Research Benchmark / 评测方式？

> 录音中提到若干 Benchmark 名称，其中部分口述 / 转写不够清晰；老师重点展开的是 **DeepResearch Bench** 及其 **RACE / FACT** 两套评测。因此整理时只把这一部分作为主答案。

### 为什么这道题重要

做了一个 Deep Research 项目后，不能只说“我感觉效果很好”。

面试官会继续问：

- 你怎么客观评测？
- 有没有公开 Benchmark？
- 怎么判断报告真的比另一个系统好？

### DeepResearch Bench

录音重点介绍了两类指标：

#### 1）RACE

主要用于评价 **最终研究报告质量**。

老师口述涉及的维度包括：

- 全面性；
- 深度 / 洞察；
- 指令遵循；
- 可读性等。

它不是简单固定一个权重，而是强调更细粒度、多维度地评价报告。

#### 2）FACT

主要关注：

- 事实丰富性；
- 引用是否可信；
- 检索的信息是否真的支持报告里的论点；
- 引用和事实是否准确。

录音还提到类似这些检查方式：

- 识别报告里的关键事实、数值和因果关系；
- 对重要论点做多来源交叉验证；
- 对验证结果给置信度；
- 对低置信度内容标记为需要进一步核实。

### 这道题怎么回答更完整

可以先说：

> 项目内部用 LLM-as-a-Judge 做在线 / 迭代反馈；项目外部还需要公开 Benchmark 做更客观的横向评测。

然后重点讲 DeepResearch Bench 的 RACE + FACT：

- RACE 看“报告写得怎么样”；
- FACT 看“事实和引用到底靠不靠谱”。

这样逻辑最清楚。

## 13. Deep Research 和 Deep Search 最大的区别是什么？能不能用 Deep Search 生成报告？

### 老师的类比

- **Deep Search = 引擎**；
- **Deep Research = 整车**。

也可以简单记成：

- Deep Search 解决“**找**”；
- Deep Research 解决“**写成完整研究成果**”。

### Deep Search 做什么

Deep Search 的核心是不断循环：

`搜索 → 阅读 → 推理 → 再搜索`

目标是围绕一个问题找到更好的答案和证据。

### Deep Research 做什么

Deep Research 深度依赖 Deep Search，因为最终报告的证据质量取决于搜索质量。

但它比 Deep Search 多出一层完整的研究组织能力，包括：

1. **规划报告结构**；
2. **把不同研究子问题并行交给多个 Deep Search / Research Agent**；
3. **整合、组织、润色所有研究结果，生成完整长报告。**

### 能不能直接用 Deep Search 生成报告

单独的 Deep Search 更像“回答一个研究问题”，并不天然负责完整报告结构。

如果想让它生成完整研究报告，需要再增加三层能力：

#### 1）规划

先生成：

- Outline；
- 目录；
- 章节结构。

#### 2）并行研究

针对不同章节 / 子问题，分别调用 Deep Search 获取详细内容。

#### 3）整合与润色

把各个研究结果拼接、重写成一份连贯的最终报告。

### 和本项目的关系

老师指出：

这三件事情，基本就是 **Supervisor** 在做的事。

真正负责“下场搜资料”的，是底层的 Research / Deep Search Agent；Supervisor 负责把这些能力组织成 Deep Research。

## 14. 了解哪些国内外商业版 Deep Research 产品？讲一个你认为做得好的

### 录音里提到的产品

国外方向举到：

- OpenAI Deep Research；
- Google Gemini Deep Research；
- Perplexity Deep Research；
- xAI / Grok 相关 Deep Research / Deep Search 产品。

国内方向举到：

- 百度相关产品；
- 通义 DeepResearch；
- Kimi Researcher；
- Step / 阶跃星辰相关研究产品等。

这道题本质上考察的是：**有没有做竞品调研，以及对行业技术路线有没有视野。**

### 如果只选一个：Kimi Researcher

老师选择 **Kimi Researcher** 作为重点案例。

原因是它代表了和传统 Workflow Agent 不同的一条路线：

> **端到端 Agentic Reinforcement Learning。**

### Workflow 路线

传统做法往往是人工设计：

`Planner → Executor → Tool Call → 固定工作流`

也就是说，人提前规定好：

- 先规划；
- 再调用工具；
- 哪一步走到哪一步。

本项目本身也更接近这种 Workflow 路线。

### Kimi Researcher 的不同点

它希望把：

- 规划；
- 决策；
- 搜索；
- 工具使用；
- 研究路径选择；

尽量内化到一个经过强化学习训练的模型本体里。

模型自己学习：

- 什么时候该搜；
- 搜什么；
- 下一步去哪；
- 什么时候停止。

而不是每一步都由人写死流程。

### 老师为什么认为这条路线有前途

录音给出的观点包括：

1. 人类不需要把所有复杂工作流都显式编码进去；
2. 模型可以通过高质量轨迹学习人类的研究 Pattern；
3. 冷启动之后，模型可以从自己的大量尝试中采样出高质量轨迹；
4. 再利用这些数据继续训练，形成持续迭代。

老师的核心判断是：**把人的研究行为轨迹内化成模型能力，是一个很值得关注的方向。**

## 15. 如果不用通用大模型，而是用强化学习训练本地 Deep Research 模型，怎么设计？

这道题承接上一题：如果希望做一个类似 Kimi Researcher / 通义 DeepResearch 的专用模型，而不是直接调用通用大模型，可以从三个方面展开。

---

### 一、数据怎么设计

录音把训练数据分成两大类。

#### 1）有固定答案、可验证的任务

例如：

- 多跳问答；
- 需要连续搜索多个事实才能得到最终唯一答案的问题；
- 数学计算 + 再基于答案继续检索的问题。

这类任务最大的优势是：**最终答案可以自动校验。**

因此容易设计 Rule-Based Reward / 可验证奖励。

#### 2）开放式研究和写作任务

例如：

- 写行业调研报告；
- 分析某个复杂开放问题。

这类任务没有唯一标准答案，因此必须采用更复杂的评估方式。

老师的观点是：**两类数据最好都要有。**

有标准答案的数据适合训练明确的搜索和推理能力；开放式数据则更贴近真实 Deep Research。

---

### 二、奖励模型怎么设计

这是整套方案里非常关键的一部分。

#### 为什么不能只打一个总分

例如有两个报告：

- 报告 A：文字流畅、逻辑不错，但引用不丰富；
- 报告 B：写作一般，但引用、证据和结构非常扎实。

这时很难用一个“0–10 总分”简单决定哪个更好。

因此 Deep Research 的奖励必须更细粒度。

#### 可以拆出的奖励维度

录音举到：

- 引用是否合理；
- 引用是否多样；
- 公式 / 计算是否正确；
- 是否能找到长尾信息；
- 结构是否合理；
- 语言是否流畅；
- 专业性；
- 逻辑严密性。

开放式任务可以用 LLM-as-a-Judge 做其中一部分，但也不应该只让一个 LLM 给单一总分。

#### 实体级奖励 / 部分正确奖励

老师举了一个多跳搜索的例子。

假设最终答案没答对，但模型已经正确找到：

- 关键人物；
- 关键电影；
- 中间核心实体。

如果只看最终答案：

- 对 = 1；
- 错 = 0；

那模型前面已经走对的很多步骤都会被完全忽略。

因此可以给 **实体级 / 中间步骤奖励**：

> 最终答案虽然错了，但如果关键实体和方向已经找对，也应该得到部分奖励。

#### 路径效率奖励

录音还提到：

在同样正确完成任务的前提下，如果一个轨迹：

- 调用更少工具；
- Token 更少；
- 路径更短；

可以给更高奖励，鼓励模型学习更高效的研究路径。

#### 防止 Reward Hacking

最终最好是复合奖励，而不是单一目标，否则模型容易为了某个分数“钻空子”。

---

### 三、训练流程怎么设计

#### 1）先做冷启动

直接对一个基础模型上复杂 Agent RL 很难，因为：

- 任务路径太长；
- 奖励稀疏；
- 一开始模型甚至不知道应该调用什么工具。

因此需要先准备少量高质量轨迹做：

- SFT；
- 或 RFT / Rejection Fine-Tuning 式冷启动。

这些轨迹可以来自：

- 人工标注；
- 更强模型生成后筛选。

先让模型掌握基本：

- 工具使用；
- 长链条推理；
- 搜索格式；
- Agent 行为模式。

然后再上 RL。

#### 2）再做强化学习

冷启动后，再通过 RL 让模型自己探索更优的行为路径。

#### 3）提高 Agentic RL 的训练效率

录音这里的术语转写成了“DPO / DOPO”，但老师随后描述的是：

- 先过滤太简单 / 太困难、没有训练价值的样本；
- Batch 不够时，不重新去环境 Rollout 新轨迹；
- 而是复制当前 Batch 里更有训练价值、有成功也有失败的难样本；
- 用这种方式填满 Batch，减少昂贵环境交互。

这一段对应的算法思想是 **DUPO（Duplicating Sampling Policy Optimization）**。

它要解决的核心问题是：

> Agent RL 的 Rollout 需要长时间和环境交互，非常慢，所以应该尽量把每一个已经获得的高价值样本利用充分。

### 整体总结

可以把训练路线概括为：

`高质量数据 → SFT / RFT 冷启动 → 多维奖励设计 → Agentic RL → 持续采样和迭代`

## 16. 了解阿里通义 DeepResearch 吗？讲一下它的思路

录音把通义 DeepResearch 看成一系列相关工作的组合，而不是孤立的一篇工作。

老师重点总结了三个方面。

---

### 一、自动化数据合成

这是录音中特别强调的创新方向。

传统做算法时，大量精力会耗在高质量训练数据的人工制作上，而人工数据：

- 成本高；
- 规模有限；
- 本身也会有噪声。

因此通义这条路线希望尽量自动生成大量复杂信息搜索任务。

录音描述的基本流程：

#### 1）构建知识图谱 / 互联网图结构

从真实网站和实体关系出发，构建包含大量：

- 实体；
- 关系；
- 网页信息。

的图结构。

#### 2）在图上采样子图

通过随机游走 / 子图采样，得到一组相关联的实体和关系。

#### 3）基于子图生成 QA

让模型基于这些信息生成问题和答案。

#### 4）做信息模糊化，提高难度

如果问题太直接，就故意隐藏 / 模糊部分条件，让模型必须：

- 多跳搜索；
- 多步推理；
- 组合多个来源；

才能得到答案。

所以核心思路是：

`图结构 → 采样 → 自动生成 QA → 信息模糊化 / 难度升级`

---

### 二、IterResearch：迭代研究范式

传统 ReAct 是：

`Thought → Action → Observation → Thought → Action → Observation ...`

所有历史不断追加到同一个上下文中。

长任务里会出现：

- 上下文越来越长；
- 噪声污染；
- 推理退化；
- 做得越久，模型反而越糊涂。

**IterResearch** 的核心是把长研究任务拆成多个独立研究回合。

每一轮：

- 只保留上一轮最关键的结论；
- 不把上一轮全部思考和工具历史原样带下来；
- 用这些核心信息重新构建一个干净的工作空间；
- 再开始下一轮思考、综合和行动。

可以理解成：

> 每一轮都“重开一个精简上下文”，但把真正重要的研究成果继承下来。

它本质上是在降低长程 Agent 的上下文管理难度。

---

### 三、训练流程

录音总结成一个比较标准的路线：

1. **CPT / Continued Pre-Training**；
2. **SFT 冷启动**；
3. **RL 强化学习。**

老师强调：

直接让基础模型在复杂多轮工具调用环境里靠 RL 找到正确路径很困难，因此先通过模仿学习 / SFT 让模型具备基础 Agent 能力，再做 RL 会更合理。

### 一句话总结

通义 DeepResearch 这条路线可以记成：

> **大规模自动合成难数据 + IterResearch 做长程上下文管理 + CPT/SFT/RL 训练专用 Agent 模型。**

---

## 17. Long-Horizon Agent 为什么是热点？这个项目可以怎么优化？

### 什么是 Long-Horizon Agent

就是一个任务需要经历很长的动作链才能完成，例如：

- 几十次；
- 上百次；

搜索、思考、工具调用和状态变化。

路径越长，错误累积、上下文爆炸、规划失效等问题越明显。

录音给出了三个重点优化方向。

---

### 一、分层规划（Hierarchical Planning）

如果所有决策都放在同一层做，路径很长时会出现巨大的组合搜索空间。

因此可以把任务做成层级结构：

- 顶层：Planner；
- 中间层：Sub-Planner；
- 底层叶子节点：Executor。

高层只决定大的子目标，底层负责具体动作。

这样可以把一个巨大长程任务拆成多个局部规划问题，降低单次规划复杂度。

录音用“把很长的 H 级搜索深度压成更分层的结构”来表达这种直觉，重点在 **层级化降低组合爆炸**，而不是强调某个严格数学公式。

---

### 二、记忆与状态管理

Long-Horizon Agent 的历史会非常长，因此必须区分并维护：

- 当前工作记忆；
- 当前子任务进度；
- 历史研究成果；
- 长期记忆；
- 环境状态。

如果记忆管理不好，就可能：

- 重复做已经做过的搜索；
- 忘记之前验证过的结论；
- 研究方向漂移；
- 在后半程失去早期关键信息。

解决办法是利用：

- 文件系统；
- 数据库；
- 持久化状态；
- 记忆检索。

把长期信息外置，需要时再取回来。

---

### 三、定期自我评估 + Re-Plan

长程任务里，一个最开始制定的计划几乎不可能从头到尾都完全正确。

所以 Agent 不能盲目按原计划一直执行，而要定期检查：

- 当前状态是否符合预期；
- 研究方向是否偏了；
- 是否已经出现关键新证据；
- 是否需要调整后续步骤。

如果偏差较大，就应该 **Re-Plan / 重新规划**。

核心思想：

`执行一段 → Check → 必要时重新规划 → 再执行`

而不是：

`一开始定好计划 → 一路执行到底`

### 三点总结

做好 Long-Horizon Agent，重点考虑：

1. **分层规划**；
2. **记忆和状态持久化**；
3. **定期评估与重新规划。**

## 18. 这个项目做完，你最大的收获是什么？

### 老师强调：一定要真实

这类问题没有标准答案。

不建议回答：

- “提升了技术能力”；
- “锻炼了编码能力”；
- “提升了实践能力”。

这种口号化表达很难打动面试官。

### 一个更好的回答方向：工程细节的重要性

录音给出的示例是：

> 最大的收获，是意识到 Agent 系统真正拉开差距的往往不是宏观算法，而是大量工程细节。

Deep Research 项目从算法流程上看，大家可能都知道：

- 先规划；
- 再任务分解；
- 再搜索；
- 再反思；
- 再精修。

真正做到工业级，不能只是“功能跑通”，而要让系统：

- 稳定；
- 鲁棒；
- 可扩展。

### 工程上真正需要处理的细节

录音提到：

- 如何提高检索质量；
- 如何管理上下文；
- 如何管理状态流转；
- 如何压缩上下文；
- URL 去重；
- URL 排序；
- 如何支持更多模型后端；
- 如何支持更多搜索后端；
- 大模型调用超时；
- 搜索超时；
- 如何避免死循环；
- 解析错误；
- 返回格式异常；
- 各种边界情况。

任何一个异常和边界问题处理不好，都可能让整个 Agent 系统崩溃。

### 最终表达

可以这样收尾：

> 做完这个项目以后，我对“一个 Demo”和“一个真正可用的工业系统”的差别理解更深了。技术方案大家可能都能想到，但最后真正决定系统质量的，是对检索、上下文、状态、异常、可观测性和扩展性这些工程细节的处理。
