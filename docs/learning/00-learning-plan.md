# 00｜学习路线与第一课：先建立整体地图

## 学习目标

不是马上背文件名或 LangGraph API，而是先回答三个问题：

1. 这个系统接收什么，产出什么？
2. 为什么要拆成多个 Agent 和多个阶段？
3. 每个角色分别负责什么？

等这三个问题清楚后，再深入代码会容易很多。

## 先把项目想成一个研究团队

把一次用户提问想成“请团队写一份有证据的深度报告”：

| 团队角色 | 项目中的对应物 | 它做什么 |
|---|---|---|
| 需求分析员 | `write_research_brief` | 把模糊问题整理成研究任务 |
| 草稿作者 | `write_draft_report` | 先写一版可修改的报告骨架 |
| 项目经理 | `Supervisor` | 判断缺什么资料、分派任务、决定何时结束 |
| 调研员 | `Researcher` | 搜索网页、反思、整理局部证据 |
| 质检员 | `Evaluator` | 给草稿的覆盖度、准确性、一致性打分 |
| 反方审稿人 | `Red Team` | 主动找漏洞、缺失和不合理之处 |
| 最终作者 | `Writer` | 汇总研究笔记和草稿，输出最终报告 |

这不是说每个角色都是独立服务；在当前代码里，它们主要是不同的图节点、子图或模型调用。

## 一次请求的故事

用户的问题从 `run.ipynb` 进入顶层图：

```text
用户问题
  → 研究简报
  → 报告初稿
  → Supervisor 分析缺口
  → 一个或多个 Researcher 并行搜索
  → 研究结果压缩成 notes
  → 草稿修订、评分、Red Team 反馈
  → Writer 生成 final_report
```

对应代码入口是 `deep_research/agent_builder.py`：它把四个顶层节点按固定顺序连接起来：

```text
START
  → write_research_brief
  → write_draft_report
  → supervisor_subgraph
  → final_report_generation
  → END
```

## 为什么不能一次调用 LLM

一次调用让同一个模型同时完成拆题、搜索、事实核验、长文组织和自我批评，常见问题是：

- 研究范围不完整，容易遗漏子主题。
- 没有足够外部证据，事实依据弱。
- 上下文过长，网页原文和推理过程互相干扰。
- 没有清晰的质量门槛，模型说“完成”不等于真的完成。
- 出错时无法定位是规划、搜索、压缩还是写作出了问题。

当前项目的拆分带来额外成本：更多模型调用、网络延迟、状态合并和失败分支。但换来的好处是职责清晰、可以并行、可以评估，也更容易定位问题。

## 现在只需要记住三句话

1. 这是一个“让多个角色协作完成深度研究”的工作流，不是单次聊天调用。
2. 外层流程负责固定阶段，Supervisor 负责动态协调，Researcher 负责搜集证据。
3. 各阶段通过共享状态传递 `research_brief`、`draft_report`、`notes` 和 `final_report`。
